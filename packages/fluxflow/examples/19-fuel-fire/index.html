grid.createGridFireSolver2 (packages/fluxflow/src/grid/grid_fire_solver2.js) -- a real fuel/combustion solver, ported from mantaflow's own fire.cpp, decoupled from any specific velocity solver: this scene builds a plain grid.createGridSolver2 directly (not createGridSmokeSolver2) and composes the fire solver's own buoyancy force into it. Fuel is supplied continuously by an SDF fuel source (grid.createSDFFuelSource2) near the bottom, the same "SDF collider/inflow/outflow" family every other scene object in this port already uses -- fuel burns down and is topped back up by the source every frame, react (this batch of fuel's own remaining reaction potential) tracks it, and density/temperature are driven by the burn itself rather than a caller-supplied source, unlike examples/17-smoke-fire's own density+temperature-only "fire". Smoke and flame render into one combined canvas: gray smoke (a real alpha-composited layer, so thin wisps let the flame glow through) sits over a flame color driven by heat alone, sharply favoring the actually-reacting core over residual warmth drifting with the smoke -- the brightest point fades toward pale blue past white, and smoke/flame each have their own independent display-only brightness gain, on top of a real solver-level flameSmoke increase for more smoke, matching how mantaflow's own scenes tune smoke and flame separately. The fuel-amount slider controls how aggressively the source tops fuel back up each frame (mode: 'set') -- near 0 the flame can't get enough fuel to ignite at all and gutters out, while at 1 (the default) it holds a steady, clean burn; values can't go above 1 here since the burn rate itself is fixed per frame, so once fuel is comfortably above what one step consumes, extra headroom stops making a visible difference (see grid_fire_solver2.js's own burn-kernel comment). Pressure options set an explicit atomicScale -- see main.js's own header comment for a real long-run stability bug (found via a 3000+-frame run) this fixes. grid.createVelocityDamping2 -- a small uniform velocity decay plugged into createGridSolver2's own (previously empty) viscosity stage -- keeps this scene's own large-scale side-to-side recirculation from dominating the whole canvas over a long run; see that file's own header comment for why a uniform decay, not a real viscosity model, is the right tool for a problem this large-scale.
