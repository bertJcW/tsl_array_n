grid.createGridFlipSolver2's new options.collider, tested against a moving collider: one SDFRigidBodyCollider2 (sdf_collider2.js) translating and rotating through an initially-resting pool of fluid. SDFRigidBodyCollider2.velocityAt() bakes its own position/angle into the built kernel graph at *build* time (a documented limitation) -- so each frame this example calls rigidCollider.update(dt) then flip.boundarySolver.setCollider(rigidCollider, ...) *before* flip.onAdvanceTimeStep(), forcing a fresh rebuild of every collider-dependent kernel with the now-current pose. This exact per-frame-rebuild pattern already existed in grid_blocked_boundary_condition_solver2.js (built for occasional collider swaps) but had never before been exercised for continuous every-frame motion in this project -- watch the fps counter for any stability regression over an extended run, not just whether the paddle visibly displaces the fluid without tunneling through it.
